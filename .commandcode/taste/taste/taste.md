# Taste
- Wants code organized into clearly understandable type/domain folders (controllers, models, pages, components grouped by concern like `public/auth/account/admin`, `ui/layout/forms`) with the proposed tree presented before the move — flat, undifferentiated folders (e.g. 24 components in one directory) are the thing to fix. Confidence: 0.5
- When a UI feature/filter is removed, prefers the matching backend/API code removed too — no dead or unused-endpoint code left behind "for safety." Confidence: 0.65
- Payment gateway credentials are owned by the database (`payment_methods` table), never by `.env`/config env vars — don't propose env-based key injection. Confidence: 0.65
- Refers to UI specs visually as screenshot files dropped in `~/Downloads` (given by filename, e.g. `2026-11-04_21-45.png`) and expects them actually opened/read before implementing, not inferred from prose alone. Confidence: 0.55
- Prefers layout consistency across a page family: all user-facing/account pages (profile, billing, preferences, donations, articles) should share the same content container width, padding, and page-heading/title styling — one page's treatment is the reference to copy everywhere, not per-page `max-w-*` or per-page header components. Confidence: 0.7
- Expects admin views to stay in parity with user-facing ones: when columns/features are added to a user page (e.g. `/my-donates`), the corresponding admin page (`/admin/donations`) must get the same treatment in the same change, including API field and i18n keys — not left as a follow-up. Confidence: 0.6
- Requires the full lint/format/type-check pipeline to run before reporting any task done: Laravel Pint, TypeScript check, ESLint, and Prettier — every task, not just PHP- or JS-touching ones. Confidence: 0.85
- Expects verification and debugging to leave the dev database untouched: no ad-hoc row/value edits, no temporary donations/tokens/cache entries left behind, and running the suite must never migrate/refresh/reset local development data (e.g. pin the test connection to in-memory sqlite so shell-exported DB env vars can't redirect it). Anything temporary must be reverted before reporting done, and irreversible writes (e.g. a live sync that flips real rows) must be cleared with him first — if values were already changed, he expects them reverted back to the exact pre-test state (rows, statuses, generated logs, cache) with the revert verified, not just an offer to do it. Confidence: 0.9
- Judges the dev database by its row counts against the seeded baseline: test-created records (and their generated logs/derived summary totals) must be deleted outright, not merely reverted to a pre-test status, since leftover test rows are what he notices first ("there should be only 2"). Confidence: 0.6
- After a successful action (pay, sync, submit), wants the page to stay put: refetches should be silent/in-place so the existing list keeps rendering and scroll position is preserved — never swap the content for a full-page loading spinner that collapses height and bounces the view to the top. Confidence: 0.55
- Wants action feedback (success, "nothing to sync"-style no-op messages, errors) delivered as toasts via the toast composable, not as inline banners/paragraphs rendered at the top of the page content. Confidence: 0.65
- Wants the project's agent instructions file (`AGENTS.md`) updated to reflect conventions and gotchas discovered during the work, rather than letting the docs drift out of date. Confidence: 0.55
- When pointing out a stale/wrong value still visible in the UI, expects a repo-wide sweep that eliminates every remaining occurrence (other pages, comments, i18n strings, and the stored data behind them) in the same change — not just the one URL he mentioned. Confidence: 0.55
- For reported bugs and behavior/design questions, wants a root-cause investigation and written plan first (what data/timeline produced the wrong state, where in the code it comes from, plus a short list of fix options with trade-offs) and expects to choose the fix himself ("share with me", "how you will fix it?", "tell me why") — not an immediate unilateral code change. He also expects the diagnosis to be proven by actually reproducing/measuring the reported scenario against real data ("please test carefully") rather than reasoned about abstractly. Confidence: 0.75
- Wants translation files kept fully in sync: a new or changed UI string must be propagated to every locale file (all ~42, identical key sets and real translations), not added to `en.json` alone or left as an English fallback — he asks for this explicitly ("please sync all lan files"). Confidence: 0.6
